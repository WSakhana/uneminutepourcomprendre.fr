# Une Minute Pour Comprendre : le site

[![Contrôle du site](https://github.com/WSakhana/uneminutepourcomprendre.fr/actions/workflows/check.yml/badge.svg)](https://github.com/WSakhana/uneminutepourcomprendre.fr/actions/workflows/check.yml)

[![Une Minute Pour Comprendre](public/assets/img/og-image.jpg)](https://uneminutepourcomprendre.fr)

Code source de **[uneminutepourcomprendre.fr](https://uneminutepourcomprendre.fr)**, le site officiel de la chaîne de
vulgarisation scientifique **Une Minute Pour Comprendre** (`@1min.pour.comprendre`). La chaîne explique en vidéo et en
images des phénomènes étonnants de la science, des animaux, du corps humain et de la nature. Le site développe chaque
vidéo en article : le mécanisme expliqué pas à pas, les limites de ce que l'on sait et les publications scientifiques
utilisées.

> **In English:** source code of the official website of *Une Minute Pour Comprendre* ("One Minute to Understand"), a
> French science communication channel on YouTube, TikTok, Instagram and Facebook. Each video becomes a sourced article.
> The site is plain static HTML and CSS, generated by a small Python script, with schema.org structured data, an RSS
> feed, `llms.txt` and AI agent skills (Codex, Claude Code) that turn a video's production folder into an article.

## Comment le site est fait

- **100 % statique** : HTML et CSS, sans framework ni backend. Le seul JavaScript sert l'année du copyright et les
  boutons « copier le lien ».
- **Un générateur Python** (`tools/build_articles.py`) transforme `content/articles/<slug>/` en pages : vidéo intégrée en
  premier, sommaire, figures, notes vers les sources, chapitres de la vidéo.
- **Référencement intégré** : données structurées schema.org (Organization, WebSite, Article, VideoObject avec chapitres,
  fil d'Ariane), Open Graph, sitemap avec images, flux RSS, `llms.txt` pour les moteurs de réponse IA, IndexNow.
- **Contrôles** : `tools/check_site.py` vérifie liens, ancres, `alt`, descriptions, canonical, Open Graph et JSON-LD, en
  local et sur chaque push (GitHub Actions).
- **Skills d'agents IA** (`.agents/skills/`) : un skill rédige l'article d'une vidéo à partir de son dossier de
  production, un autre déploie et vérifie le site en ligne.

## Structure

```text
public/                 le site, envoyé tel quel à la racine web (OVH : dossier www/)
  index.html            accueil (le bloc « Derniers articles » est généré)
  articles/             (généré) index.html = liste, <slug>/index.html = un article par vidéo
  404.html              (généré) page d'erreur, déclarée dans .htaccess
  .htaccess             cache, compression, redirections, en-têtes (Apache OVH)
  robots.txt
  sitemap.xml, feed.xml, llms.txt   (générés) sitemap avec images, flux RSS, présentation pour les moteurs IA
  <clé>.txt             clé IndexNow (publique par nature)
  assets/css/style.css, assets/js/copy-link.js
  assets/fonts/         Archivo variable (sous-ensemble français) + licence OFL
  assets/img/           visuels WebP, logo, image de partage ; articles/ (généré) images des articles
content/articles/<slug>/  source d'un article : article.toml (métadonnées, images, chapitres, sources) + body.html
.agents/skills/         skills pour Codex et Claude Code
.github/workflows/      contrôle du site à chaque push
tools/                  outils de développement, jamais envoyés en ligne
  build_articles.py     génère articles, accueil, 404, sitemap.xml, feed.xml, llms.txt
  build_assets.py       régénère les images de public/ depuis les dossiers de production
  check_site.py         contrôle statique de public/
  deploy_sftp.py        envoie public/ sur l'hébergement en SFTP
  verify_live.py        vérifie le site en ligne après un déploiement
  indexnow.py           signale les URL du sitemap à IndexNow après un déploiement
  link_skills.ps1       relie .claude/skills à .agents/skills
```

## Aperçu local

```powershell
py -3 -m pip install pillow      # une seule fois
py -3 tools/build_articles.py
py -3 tools/check_site.py
cd public; py -3 -m http.server 8000
```

Puis ouvrir http://localhost:8000. Les URL propres (`/articles/…/`) ne fonctionnent pas en `file://`.

## Articles

Chaque article est associé à une vidéo YouTube (lecteur `youtube-nocookie` en tête de page) et publié sur
`/articles/<slug>/`. Ajouter un article : créer `content/articles/<slug>/` avec deux fichiers.

- `article.toml` : titre, description, dates, mots-clés, `[video]`, `[[chapters]]`, `[images.<clé>]` et `[[sources]]`.
  Une image vient d'un fichier du dossier de production (`src`) ou de la vidéo finale (`video_time`, `box` ; ffmpeg requis).
- `body.html` : une `<section id="…">` par partie, avec `{{figure:clé}}`, `{{cite:S1}}` et `{{chapitre:secondes}}`.

Un même article peut réunir plusieurs vidéos : garder `[video]` pour la première et ajouter `[[additional_videos]]`
pour les suivantes (mêmes métadonnées). Le build affiche tous les lecteurs en tête et produit un `VideoObject` par vidéo.
Les images des articles sont recadrées individuellement et affichées dans une limite de 640 × 420 px, sans déformation.

Le build refuse une source citée mais absente, listée mais jamais citée, ou un « TODO » restant. Format détaillé :
[`.agents/skills/umpc-site-article/references/article-format.md`](.agents/skills/umpc-site-article/references/article-format.md).
Ne jamais modifier à la main `public/articles/`, `public/404.html`, `sitemap.xml`, `feed.xml`, `llms.txt` ni le bloc
entre `<!-- articles:start -->` et `<!-- articles:end -->` de `public/index.html` : ils sont réécrits à chaque build.
Après une modification du CSS ou du JS, relancer le build : les liens portent une empreinte `?v=…` qui renouvelle le cache.

## Synchronisation des articles avec YouTube

Les brouillons restent dans `content/articles/`. Le champ racine `status = "draft"` les exclut du build, des listes,
du sitemap, du flux RSS et de `llms.txt`. Aucun aperçu de brouillon n’est écrit dans `public/`. Une ancienne page
locale devenue brouillon bloque le build jusqu’à son archivage par la synchronisation.

`tools/sync_youtube_articles.py` consulte la chaîne authentifiée en lecture seule. Il publie uniquement les articles
`ready = true` dont **toutes** les vidéos sont `public`, traitées et intégrables. Une date prévue passée ne suffit jamais.
Les programmations sont relues à chaque passage. Les vidéos privées, non répertoriées, absentes ou à venir restent
exclues. Si une vidéo devient privée, sa page générée est archivée localement et l’accès distant est bloqué par
`.htaccess`, sans suppression de données sur OVH.

```powershell
py -3 tools/sync_youtube_articles.py             # lecture et suivi seulement
py -3 tools/sync_youtube_articles.py --prepare   # build local des pages éligibles, sans envoi
py -3 tools/sync_youtube_articles.py --publish   # build, check, simulation, SFTP, vérification et IndexNow
```

L’authentification réutilise le jeton Windows DPAPI de `.youtube_private/oauth.dpapi` et le client OAuth existant dans
le dossier désigné par `UMPC_YOUTUBE_AUTH_DIR` (par défaut `G:\My Drive\@UMPC`). Aucun secret ne va dans ce dépôt.
La tâche Windows reste strictement en lecture seule sur YouTube : elle ne modifie aucune description, aucun titre
ni aucun statut de vidéo. Elle synchronise et publie uniquement les articles.
La mise à jour des descriptions est un outil manuel distinct, à utiliser seulement sur demande explicite.
Il transfère les références dans l’article, puis remplace les listes de sources et crédits par son lien.
Pour une vidéo publique, il vérifie la page en ligne. Avec `--include-scheduled`, il peut préparer la description
d’une vidéo programmée avant sa sortie, après avoir vérifié les références conservées dans son brouillon.
Le lien d’article est alors réservé : l’article reste inaccessible jusqu’à sa publication automatique.
Chaque écriture conserve les autres propriétés éditables du `snippet`, ne touche pas au `status` et fait l’objet
d’une sauvegarde puis d’une relecture. Les textes introductifs, chapitres, hashtags et mentions IA sont conservés.

```powershell
py -3 tools/update_youtube_article_links.py --consolidate  # transfert dans les sources locales d’articles
py -3 tools/update_youtube_article_links.py               # audit sans écriture YouTube
py -3 tools/update_youtube_article_links.py --apply       # descriptions des seules vidéos avec article public vérifié
py -3 tools/update_youtube_article_links.py --apply --include-scheduled  # sur demande : inclure les vidéos programmées
```

Une nouvelle vidéo peut être reliée à un brouillon sans ID seulement si son nom de fichier d’upload correspond
de façon unique au projet et si sa durée est cohérente. Aucun rapprochement approximatif de titres n’est accepté.
`editorial_ready = false` empêche ce rapprochement automatique lorsque le contenu ou la production manque.

La tâche Windows `UMPC - Synchronisation articles YouTube` utilise `tools/run_article_sync.py` toutes les quinze
minutes et à l’ouverture de session. Elle fonctionne sans Codex ouvert. Le PC doit être allumé, connecté, avec la
session utilisateur ouverte et le lecteur Google Drive disponible. Les passages manqués sont repris à la prochaine
occasion. Les identifiants SFTP viennent des variables utilisateur ou machine `UMPC_SFTP_HOST`, `UMPC_SFTP_USER`
et `UMPC_SFTP_PASSWORD`, jamais de la définition de tâche. Le script utilise `.venv/Scripts/pythonw.exe`, sans fenêtre.

```powershell
py -3 -m venv --system-site-packages .venv
pwsh -NoProfile -File tools/install_article_sync_task.ps1
```

Les exécutions concurrentes sont exclues. Un échec d’API ne publie rien ; un échec d’envoi ou de vérification est
repris sans marquer le déploiement réussi. Un envoi est ignoré si le contenu public n’a pas changé. Le contrôle
`tools/verify_article_publication.py` compare le HTML en ligne aux fichiers locaux et vérifie les 404 des brouillons.
Le dernier résultat et les erreurs sont dans `tracking/sync-state.local.json` et `tracking/sync.log`.

Le suivi contient les IDs, statuts et dates YouTube, les URL, les descriptions proposées et les limites de vérification.
Les fichiers `tracking/*.private.json`, `*.private.md` et `*.private.csv` ne sont ni versionnés ni déployés.
Les sources et illustrations d’un article restent dans ses fichiers habituels. Les tables `[[media_credits]]`
complètent les crédits des figures avec les médias réellement identifiés dans la vidéo.

## Skills (Codex et Claude Code)

- **`umpc-site-article`** : à partir d'une URL YouTube de la chaîne et du dossier de production de la vidéo, rédige
  `content/articles/<slug>/` (texte éditorial, images, sources scientifiques réellement utilisées), construit et contrôle
  le site, et donne la ligne à coller dans la description YouTube.
- **`umpc-site-deploy`** : build, contrôles, envoi SFTP, vérification en ligne, notification IndexNow.

Codex lit `.agents/skills/` directement. Claude Code lit `.claude/skills/`, une jonction locale non versionnée : la créer
après un clonage avec `powershell -ExecutionPolicy Bypass -File tools/link_skills.ps1`. Instructions communes :
[`AGENTS.md`](AGENTS.md).

## Mise en ligne (mainteneur)

```powershell
py -3 -m pip install paramiko            # une seule fois
setx UMPC_SFTP_HOST "ftp.clusterXXX.hosting.ovh.net"   # une seule fois, valeurs de l'espace client OVH
setx UMPC_SFTP_USER "<utilisateur>"
py -3 tools/deploy_sftp.py --dry-run     # simulation, sans connexion
py -3 tools/deploy_sftp.py               # envoie public/ dans www/
py -3 tools/verify_live.py               # vérifie le site en ligne
py -3 tools/indexnow.py                  # signale les URL à IndexNow (Bing, Yandex...)
```

Le mot de passe est demandé au clavier ou lu dans `UMPC_SFTP_PASSWORD`. Aucun identifiant n'est écrit dans le dépôt. Le
script remplace des fichiers mais n'en supprime jamais en ligne.

**Ne pas activer GitHub Pages** sur ce dépôt : une copie de `public/` sur `github.io` dupliquerait le contenu du site.
